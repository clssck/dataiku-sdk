# Project lint rules

`index.ts` implements the `dss` Oxlint plugin locally. It is repository code, not a vendored plugin.

- `no-chained-type-assertions`: rejects nested `as` and angle-bracket assertions, including transparent expression wrappers.
- `no-widen-then-assert`: rejects direct assertions on unchanged local bindings explicitly widened to `any`, `unknown`, `object`, an empty object type, or a broad `Record`, when the initializer has explicit concrete type evidence or is a literal. External unknown values and incrementally constructed records remain valid boundaries.
- `no-reduce-accumulator-copy`: identifies the accumulator binding of inline `reduce`/`reduceRight` callbacks and rejects repeated copying through array copy methods, `Array.from`, `Object.assign` into another target, object enumeration, `structuredClone`, and `Map`/`Set` constructors. Shadowed identifiers are separate bindings.
- `no-uncoded-errors` (`src/`): rejects raising a built-in `Error`; raise a coded error (`DataikuError`, `ClientValidationError` with a stable error code, or `UsageError`).
- `no-usage-literals` (`src/`): rejects hand-written usage lines; render them with `commandUsage(resource, action)` from `src/cli/command-syntax.json`.
- `no-direct-process-env` (`src/`): rejects reading `process.env` outside the env/runtime/config modules.
- `no-raw-json-parse-in-resources` (`src/resources/`): rejects an unguarded `JSON.parse` of a DSS body, so a non-JSON body becomes a classified error instead of a `SyntaxError`.
- `no-raw-number-coercion` (`src/cli/`, except `coerce.ts`): rejects `Number()`, `parseInt()`, `parseFloat()` (also `Number.parseInt`/`Number.parseFloat`) and unary `+` applied to a flag read: a member or index access on `f` or `flags`, directly or through one local `const` of the same function initialized from such an access. A blank flag is `""` and `Number("")` is `0`; use `num(value, "--flag")` or `numFlag(flags, [...])` from `src/cli/coerce.ts`, which reject blanks. Values that reach the coercion through a second binding, a parameter, or a call are not tracked.
- `no-unbounded-response-body` (`src/resources/`, `src/cli/`): rejects an argument-less `.text()`, `.json()`, `.arrayBuffer()`, `.bytes()`, `.blob()` or `.formData()` on anything except a `Bun.file(...)` call or a `new Blob(...)`/`new File(...)`. Buffered bodies go through the client's bounded readers (`getText`, `postText`, `readBoundedBytes`, ...), which hold the size cap (`maxResponseBodyBytes`) and the deadline; `src/client.ts`, where they live, is out of scope. Receiver naming was not needed: on the repository the rule had two findings (both real, since fixed) and no false positives.
- `no-implicit-stdin` (`src/cli/commands/`, `src/cli/helpers/`): every use of `readStdinText` (call or reference, not its import or declaration) needs either an enclosing `if`, ternary, or `&&` whose test mentions the stdin flag (`.stdin`, `"stdin"`) or compares against the `-` marker, or an earlier `requireContentSource(...)` call in one of its enclosing functions (the content-source commands call it first and then fall through a conditional chain to the stdin reader). The shared input readers in `src/cli/coerce.ts` are out of scope.
- `no-chmod-after-write` (`src/`): rejects `chmod`/`chmodSync`/`fchmod`/`fchmodSync` to an owner-only literal mode (`0o600`, `0o700`, `0o400`) in a function that also calls `writeFile`/`writeFileSync`/`Bun.write` without a `mode` option; the file is readable by others between the write and the chmod. Create owner-only files with the mode at open time. A mode held in a variable is not tracked.

The native `oxc/no-accumulating-spread` rule covers spread copies in reductions and loops. Ordinary immutable mapping remains allowed. All of these checks are errors. They are syntax and lexical-scope checks, not TypeScript assignability analysis or exhaustive performance analysis. No automatic fixes are offered: changing a type boundary or mutation strategy requires review.

Scope lives in `.oxlintrc.json` overrides: every file with an active `dss/*` rule pays an AST transfer into the JS plugin (about 1.3 s of a 2 s run when every rule covered every file). The type-assertion and accumulator rules run on `src/`, `tools/` and `scripts/` (chained assertions not on scripts); the error, usage, environment, and chmod rules on `src/`; the JSON-parse rule on `src/resources/`; the number-coercion rule on `src/cli/`; the response-body rule on `src/resources/` and `src/cli/`; the stdin rule on `src/cli/commands/` and `src/cli/helpers/`. Tests are exempt. Rules that also check their own path (`no-uncoded-errors`, `no-direct-process-env`, `no-raw-number-coercion`, …) keep doing so, so they behave the same when run alone. `no-restricted-imports` bans `node:string_decoder`, `node:child_process`, `fileURLToPath` from `node:url`, and `createHash` from `node:crypto` outside tests and scripts in favour of the Bun-native equivalents. The built-in `no-restricted-globals` bans `fetch`, `XMLHttpRequest` and `WebSocket` in `src/` (every HTTP call goes through `DataikuClient`) and is off for `src/client.ts`.

`bun run lint` runs with `--deny-warnings` and type-aware (`options.typeAware` in `.oxlintrc.json`, backed by `oxlint-tsgolint`), so promise, stringification, and exhaustiveness rules see TypeScript types. `await-thenable` and `no-unnecessary-type-arguments` are off in `tests/`: bun-types types `expect(...).resolves.toEqual(...)` as `void`, though awaiting it is required, and `expect<unknown>(value)` is not redundant there because the explicit type argument lets matchers take any value.

`bun run verify` type-checks the plugin; `bun run lint` lints it along with the SDK and CLI. `bun test tests/oxlint-rules.test.ts` exercises the actual Oxlint process against accepted and rejected programs. Keep `oxlint`, `@oxlint/plugins` and `oxlint-tsgolint` pinned to exact versions (no ranges): `oxlint` and `@oxlint/plugins` use the same version; `oxlint-tsgolint` has its own version line and is upgraded together with `oxlint`, after `bun run lint` and the rules test pass.
